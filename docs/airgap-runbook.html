인터넷이 닫힌 k3s 노드에 EVA 스택(iam · app · agent · vision)을 올리는 절차입니다. iam·app 및 Agent/Qdrant의 Harbor snapshot 경로는 실제 서버에서 검증했고, vision은 같은 bundle·Harbor 준비 절차를 사용합니다. 호스트가 두 개라는 점이 이 작업의 핵심이라 모든 단계에 실행 위치를 표시했고, ⚑ 는 통과하지 못하면 다음으로 가면 안 되는 지점입니다.

Qdrant snapshot 방식

Agent 3.1.0의 Qdrant snapshot은 기존 local_pv와 Harbor OCI artifact 방식 중 하나를 선택합니다. 이 runbook은 USB 설치에서 node hostPath를 미리 seed하지 않아도 되는 harbor 방식을 권장합니다.

구분local_pv (기존 호환)harbor (권장)
Qdrant valuesvalues-k3s.yamlvalues-k3s.harbor.yaml
snapshot 전달대상 노드 hostPath/PV 사전 시딩Local Harbor OCI artifact
배포 변수eva_agent_qdrant_snapshot_source=local_pveva_agent_qdrant_snapshot_source=harbor
새 PVC의 노드 제약단일 노드 사전 시딩 필요Pod와 모든 node가 Harbor endpoint에 도달해야 함

두 방식을 섞으면 안 됩니다. 준비 서버의 EVA_AGENT_QDRANT_SNAPSHOT_SOURCE/EVA_AGENT_QDRANT_VALUES_FILE와 대상 서버의 Qdrant values/source 변수를 모두 같은 방식으로 맞춥니다.

<artifact-tag>|<snapshot-file>|<logical-collection>

eva_manual_qwen3vl_collections|eva_manual_qwen3vl_20260824.snapshot|eva_manual_qwen3vl

values-k3s.harbor.yaml의 SNAPSHOT_SPECS가 artifact tag·snapshot 파일·collection의 단일 기준입니다. 단일 노드 Local Harbor에는 Qdrant(eva/qdrant:v1.18.2), snapshot-sync(eva/eva-agent-qdrant-snapshot-sync:0.1.0), chart test용 eva/bci-base:latest, snapshot OCI artifact(eva/qdrant-snapshots:<tag>)가 있어야 합니다.

docker 이미지 스토어 확인 준비 서버 ⚑

containerd 이미지 스토어를 쓰는 docker 는 docker save 에서 레이어를 빼먹은 tar 를 만듭니다. 대상 서버에서 docker load 는 성공한 듯 보이지만 push 가 failed to read config content 로 실패합니다.

docker info --format '{{.DriverStatus}}'

출력에 containerd/snapshotter 가 보이면 끄고 재시작합니다. 기존 daemon.json 에 insecure-registries 등이 있으면 지우지 말고 features 항목만 추가하세요.

sudo cat /etc/docker/daemon.json 2>/dev/null

sudo tee /etc/docker/daemon.json >/dev/null <<'EOF'
{ "features": { "containerd-snapshotter": false } }
EOF
sudo systemctl restart docker
⚑ 멈춤

이 설정 없이 만든 bundle 은 04번 검증에서 걸립니다. 걸리지 않고 넘어가더라도 대상 서버에서 push 가 실패하므로, 여기서 확실히 해두는 게 가장 저렴합니다.

대용량 단일 docker save가 멈추거나 USB/rsync 재개 단위를 작게 해야 하면 image별 tar를 대신 씁니다. 완성된 파일은 건너뛰므로 중단 후 같은 블록을 다시 실행할 수 있습니다.

mkdir -p install/images/tars
n=0
while IFS= read -r image; do
  n=$((n + 1))
  archive=$(printf 'install/images/tars/%02d-%s.tar' "$n" "$(basename "${image%%:*}")")
  if [ -s "$archive" ]; then echo "[skip] $archive"; continue; fi
  docker save "$image" > "$archive"
done < install/images/images-pulled.txt

find install/images/tars -name '*.tar*' -size -10M -print

마지막 find는 아무것도 출력하지 않아야 합니다. 수동 USB bundle에는 image tar(또는 단일 archive) 외에 install/qdrant-snapshots/, install/qdrant/, install/eva-agent/, install/tools/oras, 모델과 deployer의 role/playbook 전체를 함께 넣습니다.

스크립트가 eva/<이름> 으로 올리면서, 레지스트리 주소가 없는 이미지는 Docker Hub 원본 경로로도 한 벌 더 올립니다 (library/busybox, library/mysql, bitnami/kubectl …). 다음 단계의 mirror 가 그 경로를 찾습니다. 필요한 Harbor project 도 자동으로 만듭니다.

[mirror] 자동 선택: busybox:latest mysql:8.0.42-bookworm bitnami/kubectl:latest ...
[project] 생성: bitnami
[mirror] bitnami/kubectl:latest -> localhost:32080/bitnami/kubectl:latest
grep -E 'qdrant|snapshot-sync|bci-base' install/images/repository-mapping.txt

Harbor 설치가 install/harbor-endpoint.yaml을 생성합니다. 단일 서버에서는 Agent playbook이 이 파일의 Pod 접근 endpoint를 Qdrant snapshot sidecar에 자동 적용합니다. Pod 안의 localhost:32080은 Harbor host가 아니라 그 Pod 자신이므로 sidecar endpoint로 고정하면 안 됩니다.

Qdrant snapshot은 Docker image가 아니라 eva/qdrant-snapshots:<tag> OCI artifact입니다. 따라서 push_images_to_repository.sh만으로는 올라가지 않으며, 다음 독립 seed 단계가 필요합니다.

08a

Qdrant snapshot OCI artifact seed 대상 서버 ⚑

이 단계는 setup_harbor.sh나 site_eva_agent.yaml의 일부가 아닙니다. 순서는 반드시 Harbor 설치 → 일반 image push → snapshot OCI artifact push → Agent/Qdrant 배포입니다. 일반 image push가 먼저 끝나 eva project가 만들어져 있어야 합니다.

EVA_AGENT_QDRANT_VALUES_FILE=values-k3s.harbor.yaml \
  REPOSITORY_REGISTRY=localhost:32080 REPOSITORY_PROJECT=eva \
  ./install/push_qdrant_snapshots_to_harbor.sh

cat install/qdrant-snapshots/harbor-artifacts.txt

표준 Local Harbor(~/.local/share/eva-harbor/harbor/harbor.yml)에서는 helper가 실제 관리자 비밀번호를 자동으로 읽어 ORAS login을 합니다. 별도 Harbor이거나 기본 설치 경로라면 Pod와 대상 node에서 도달 가능한 registry endpoint 및 비밀번호를 함께 지정합니다.

REPOSITORY_PASSWORD='<Harbor 관리자 비밀번호>' \
REPOSITORY_REGISTRY=<Pod와-node에서-도달-가능한-host:32080> \
REPOSITORY_PROJECT=eva \
./install/push_qdrant_snapshots_to_harbor.sh
⚑ 멈춤

선행 조건

모델 캐시(install/models/agent/hf, install/models/vllm/hf)가 대상 서버에 있어야 합니다 — role 이 두 경로를 assert 합니다. 프로파일이 다운로드 때와 다르면 Harbor 에 없는 vllm 이미지를 찾게 됩니다. values-k3s.harbor.yaml과 eva_agent_qdrant_snapshot_source=harbor는 함께 지정해야 합니다.

role은 offline Qdrant chart, 선택한 Harbor values, post-renderer를 workspace로 복사하고 <harbor_base_url>/<harbor_registry>/<harbor_project> placeholder를 repository_registry/repository_project로 치환해 Qdrant·chart test image를 Harbor로 고정합니다.

Harbor snapshot profile에서 repository_registry와 repository_project는 Qdrant 본체, snapshot-sync sidecar, OCI snapshot artifact의 registry/repository가 됩니다. 단일 노드 Local Harbor의 localhost:32080은 Pod loopback 문제가 있으므로 role이 node InternalIP:32080으로 자동 변환하며, install/harbor-endpoint.yaml이 있으면 그 endpoint를 우선 사용합니다.

qdrant-snapshot-harbor는 Harbor 설치 때 생기는 값이 아니라, Harbor snapshot mode에서 role이 Helm 설치 직전에 만드는 Qdrant 전용 Kubernetes Secret입니다. 표준 Local Harbor 경로의 harbor.yml이 있으면 실제 관리자 비밀번호를 읽고, 별도 Harbor에서는 -e harbor_admin_password='<Harbor 관리자 비밀번호>'를 지정합니다.

이 playbook은 artifact를 Harbor에 push하지 않습니다. 08a의 artifact seed가 선행되어야 하며, 배포 중 sidecar가 artifact를 pull한 뒤 collection을 restore합니다.

여러 k3s node 또는 별도 Harbor에서는 localhost:32080 대신 Pod와 모든 node에서 도달 가능한 DNS/IP:port를 씁니다.

ansible-playbook -i inventory.ini site_eva_agent.yaml \
  -e repository_mode=remote_repository \
  -e @install/harbor-endpoint.yaml \
  -e harbor_admin_password='<Harbor 관리자 비밀번호>' \
  -e eva_agent_qdrant_values_file=values-k3s.harbor.yaml \
  -e eva_agent_qdrant_snapshot_source=harbor

Pod 내부의 localhost는 Harbor host가 아니라 그 Pod 자신입니다. snapshot sidecar의 HARBOR_REGISTRY를 localhost:32080으로 수동 고정하지 않습니다.

kubectl get pods -n eva-agent -l app.kubernetes.io/instance=eva-agent-qdrant -w

kubectl get pods -n eva-agent -l app.kubernetes.io/instance=eva-agent-qdrant \
  -o jsonpath='{range .items[*]}{range .spec.containers[*]}{.image}{"\n"}{end}{range .spec.initContainers[*]}{.image}{"\n"}{end}{end}' \
  | sort -u

kubectl logs -n eva-agent statefulset/eva-agent-qdrant \
  -c qdrant-snapshot-sync --tail=100

kubectl rollout status statefulset/eva-agent-qdrant \
  -n eva-agent --timeout=900s

kubectl exec -n eva-agent statefulset/eva-agent-qdrant \
  -c qdrant-snapshot-sync -- \
  curl -fsS http://127.0.0.1:6333/collections/eva_manual_qwen3vl

정상 sidecar log에는 pulling, restoring이 보이고, 현재 collection은 status: green, points_count: 62입니다. 정상 순서는 artifact pull → /qdrant/snapshots/bootstrap에 snapshot 저장 → collection restore → readiness file 생성 후 StatefulSet Ready입니다. oras pull 401은 Secret 비밀번호 또는 Pod용 Harbor endpoint 문제이고, artifact not found는 08a seed 누락 또는 profile/tag 불일치입니다.

증상원인조치
ErrImagePull / NotFound새 images-pulled.txt 기준 image push 미실행tar load 후 image push를 재실행하고 mapping·crictl pull로 확인
Pod image에 <harbor_base_url>가 남음오래된 Harbor values 또는 수동 Helm 배포최신 bundle/role로 재배포하고 image·artifact를 다시 seed
snapshot source/profile 불일치harbor source와 values-k3s.yaml을 섞음준비·push·배포를 모두 Harbor values + harbor로 통일

Qdrant만 재배포하더라도 images-pulled.txt 또는 SNAPSHOT_SPECS가 바뀌었다면 일반 image push와 08a snapshot artifact push를 둘 다 다시 실행합니다.

보류 이슈

기능 검증과 별개로 후속 조치가 필요한 보안 항목

권한

roles/config/tasks/scret.yaml은 현재 config/<host>/scret.yaml을 0644로 생성합니다. 이 파일에는 cluster-admin 권한의 argocd-manager ServiceAccount bearer token이 있어 같은 서버의 다른 로컬 사용자가 읽고 재사용할 수 있습니다. 2026-08-27 Agent/Vision Airgap 설치 테스트에서 확인했으며 기능 영향은 없습니다. 후속으로 task의 출력 권한을 0600으로 바꾸고 role을 대상 서버에 전달한 뒤 site_eva_config.yaml을 재실행합니다. 파일 내용은 출력하지 않고 권한만 검증합니다.

차트 쪽 미해결 과제: eva-iam 3.1.0/3.1.1 의 busybox·bitnami/kubectl 3곳과 eva-app 3.1.4 의 mysql 1곳이 이미지 주소를 values 로 바꿀 수 없게 하드코딩되어 있습니다. 같은 차트의 다른 컨테이너들은 .Values.*.image.repository 패턴을 쓰므로 그 패턴에 맞추면 mirror 우회가 불필요해집니다. 비밀번호는 아직 전부 차트 공개 기본값입니다.
