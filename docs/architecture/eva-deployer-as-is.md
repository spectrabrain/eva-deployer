# EVA Deployer AS-IS Architecture Investigation

## 1. Document Purpose

This document records the current EVA Deployer architecture as verified from the repository on the investigation baseline below. It is intentionally evidence-first.

Primary goals:

- Describe the current structure without redesigning it.
- Link each major claim to repository evidence.
- Register the main structural problems as `ASIS-xxx` issues.
- Provide a source-backed baseline for the TO-BE design.

- `UNKNOWN`: Not verifiable from the inspected repository scope.

## 5. High-Level Summary

Current EVA Deployer already separates Infra-first and Solution-later execution at the playbook flow level, but not at the source layout, versioning, packaging, or release identity level. The repository currently combines:

- Infra installation logic
- Solution installation logic
- Offline asset acquisition scripts
- Offline artifact materialization under `install/`
- Customer-editable values samples
- Generated deployment config under `config/<host>/eva.yaml`

That combination is functional, but it blurs lifecycle boundaries between product source, build-only acquisition logic, customer data, and generated outputs.

## 8. Verified Current Architecture Statements

### 8.1 Execution Order Is Split, Source Layout Is Not

- Infra execution order is explicit in `site_infra.yaml`; see `SE-001`.
- Aggregate EVA solution execution order is explicit in `site_eva.yaml`; see `SE-002`.
- Component-only entrypoints exist for app, agent, vision, and iam; see `SE-003` to `SE-006`.

Status: `CONFIRMED`

### 8.2 `versions.json` Is A Shared Control Plane For Both Playbooks And Acquisition Scripts

- Playbooks import `versions.json` directly; see `SE-007`.
- Install scripts import version-derived shell variables via `load_deploy_versions`; see `SE-008`.

Status: `CONFIRMED`

### 8.3 Repository Mode Handling Is Duplicated Across Multiple Entry Points

- Repository mode is defined as Cloud, Remote, Local in `README.md`; see `SE-009`.
- Similar `repository_mode` and `airgap_mode` derivations appear across multiple playbooks and roles; see `SE-010`.

Status: `CONFIRMED`

### 8.4 Helm Installation Is Mediated By Ansible, Not A Direct Chart-Only Workflow

- App, agent, vision, and iam each select repo chart versus offline chart inside the role logic; see `SE-011` to `SE-014`.
- Each role exports default values via `helm show values`; see `SE-015` to `SE-018`.
- Each role renders or applies deployer-owned override values before installation; see `SE-019` to `SE-022`.

Status: `CONFIRMED`

### 8.5 Host-Specific And Generated Configuration Are Separate Inputs With Different Ownership

- Generated config is written under `config/<host>/eva.yaml`; see `SE-025`.
- That generated config is required by aggregate EVA deploy, agent-only deploy, and vision-only deploy; see `SE-026`.
- App and IAM also support human-authored host-specific values files; see `SE-023`, `SE-024`.

Status: `CONFIRMED`

### 8.6 Chart Contract Knowledge Is Embedded Inside Roles

- App and IAM roles gate behavior on chart version or chart keys; see `SE-027`, `SE-028`.
- Agent roles fetch additional release assets and plugins to complete a deploy; see `SE-029`.

Status: `CONFIRMED`

### 8.7 `install/` Is Both Source-Adjacent Acquisition Logic And Build Output Storage

- Scripts under `install/` create the on-disk output tree under the same `install/` root; see `SE-030`, `SE-031`.
- Current airgap docs refer to copying prepared `install/` content to other environments; see `SE-032`.

Status: `CONFIRMED`

### 8.8 Rollback, Resume, And Audit Coverage Are Uneven

- Offline package audit exists through `dpkg --audit`-based tooling; see `SE-033`.
- Dedicated rollback or resume workflows were not found in the inspected source set; see `SE-034`.

Status: `CONFIRMED` for the scoped evidence above.

## 9. AS-IS Problem Register

### ASIS-001. Infra And Solution Are Separated In Execution, But Not In Source Lifecycle

- Phenomenon:
  Infra and Solution use different entrypoints and roles, but live in the same root source structure and share the same packaging area.
- Source evidence:
  `SE-001`, `SE-002`, `SE-006`, `SE-030`, `SE-031`
- Impact:
  Source browsing, release ownership, and version scoping are harder than the actual runtime sequence implies.
- Risk:
  Changes intended for one lifecycle can unintentionally couple to the other.
- Required TO-BE conditions:
  Separate source trees, separate version catalogs, separate release identities, explicit dependency rules.

### ASIS-002. `versions.json` Is A Shared Version Catalogue Across Infra, Solution, And Acquisition Scripts

- Phenomenon:
  One file carries chart, image, and tool versions consumed by both Ansible playbooks and shell acquisition scripts.
- Source evidence:
  `SE-007`, `SE-008`
- Impact:
  Build-time and install-time concerns are not separated.
- Risk:
  A version change for one lifecycle can affect another lifecycle without a separate release boundary.
- Required TO-BE conditions:
  Split version catalogs by component boundary and bind installs to immutable manifests or digests.

### ASIS-003. Environment Variables Can Override The Shared Version Catalogue At Acquisition Time

- Phenomenon:
  `load_deploy_versions` exports only when a shell variable is currently empty and documents that environment values silently win.
- Source evidence:
  `SE-008`
- Impact:
  Acquisition results can differ from the committed version file.
- Risk:
  Reproducibility is weakened unless build logs are preserved and checked.
- Required TO-BE conditions:
  Explicit build manifest capture, immutable artifact metadata, and controlled override policy.

### ASIS-004. Repository Mode Logic Is Duplicated Across Entry Points And Roles

- Phenomenon:
  Cloud, Remote, and Local branching is implemented repeatedly across playbooks and roles.
- Source evidence:
  `SE-009`, `SE-010`, `SE-014`, `SE-032`
- Impact:
  Behavior is spread across multiple files instead of one contract.
- Risk:
  Divergent handling between components is more likely over time.
- Required TO-BE conditions:
  Central installation contract for delivery mode, registry resolution, and offline behavior.

### ASIS-005. Helm Deployment Depends On Deployer-Rendered Overrides

- Phenomenon:
  The deployer exports default chart values, renders its own override templates, optionally loads host-specific values, then runs Helm.
- Source evidence:
  `SE-011` to `SE-024`
- Impact:
  A chart-only or values-only emergency change is not automatically independent from Deployer logic.
- Risk:
  Operational hotfixes can expand into Ansible-role changes.
- Required TO-BE conditions:
  Formal values ownership, precedence contract, and patch packaging rules that isolate mutable overlays from immutable base artifacts.

### ASIS-006. Generated Config And Customer Overrides Have Different Ownership, But Are Stored Near Product Source

- Phenomenon:
  Generated config is written under `config/<host>/eva.yaml`, and host-specific values are expected under repository-local `values/*.yaml` paths.
- Source evidence:
  `SE-023`, `SE-024`, `SE-025`, `SE-026`
- Impact:
  Product source, customer data, and generated state are not strongly separated.
- Risk:
  Repository-local workflows can blur what is releasable source versus runtime site data.
- Required TO-BE conditions:
  Separate ownership boundary for product source, customer site data, and generated runtime state.

### ASIS-007. Chart Contract Knowledge Is Embedded Inside Roles

- Phenomenon:
  Roles explicitly validate chart versions, chart keys, and schema-sensitive options.
- Source evidence:
  `SE-027`, `SE-028`, `SE-029`
- Impact:
  Chart evolution can require role changes even when the desired operational change is small.
- Risk:
  Emergency response remains tightly coupled to the installer implementation.
- Required TO-BE conditions:
  Stable installation contract, chart schema capture in artifact metadata, and allowed patch scopes that avoid editing core role logic for routine chart drift.

### ASIS-008. External Release Assets For Agent Dependencies Are Multi-Origin And Role-Specific

- Phenomenon:
  Agent deploy logic fetches or copies extra values files, secret values, qdrant plugin metadata, and post-renderer scripts from multiple release paths.
- Source evidence:
  `SE-029`, `SE-030`
- Impact:
  The operational release unit is wider than a chart `.tgz` alone.
- Risk:
  Missing or mismatched side assets can break deploys or force ad hoc fixes.
- Required TO-BE conditions:
  Artifact manifest must enumerate all required side assets and bind them to a base artifact digest.

### ASIS-009. `install/` Mixes Build Logic And Build Outputs In The Same Tree

- Phenomenon:
  The same `install/` tree contains acquisition scripts, manifests, and downloaded result directories.
- Source evidence:
  `SE-030`, `SE-031`
- Impact:
  Source review and release packaging boundaries are unclear.
- Risk:
  Large downloaded content can be confused with source-owned content, and artifact reproducibility is harder to audit.
- Required TO-BE conditions:
  Keep source acquisition manifests in source, and split temporary work, cache, and final distribution outputs outside source.

### ASIS-010. Airgap Delivery Uses Prepared Repository Content, But Not Component-Named Immutable Release Artifacts

- Phenomenon:
  Current documentation and scripts refer to copying `install/` content or its subtrees into remote or local repository workflows.
- Source evidence:
  `SE-030`, `SE-031`, `SE-032`
- Impact:
  Delivery works operationally, but release identity is implicit in directory content rather than explicit component artifacts.
- Risk:
  Cloud and Airgap distribution are less auditable than digest-bound artifacts.
- Required TO-BE conditions:
  Same immutable component artifact for Cloud and Airgap, with distribution path as a transport concern only.

### ASIS-011. Rollback, Resume, State, And Audit Are Incomplete Or Unevenly Standardized

- Phenomenon:
  Offline `.deb` audit and recovery exist, but no dedicated repository-scoped install state ledger, rollback workflow, or resume workflow was found in scope.
- Source evidence:
  `SE-033`, `SE-034`
- Impact:
  Operators rely on tool-specific knowledge rather than a single deploy-state contract.
- Risk:
  Recovery behavior will vary by component and operator skill.
- Required TO-BE conditions:
  Persistent install state, audit output schema, rollback rules, and checkpoint-based resume contract.

### ASIS-012. Customer Data Placement Is Not Explicitly Separated From Product Source

- Phenomenon:
  Sample values, actual host-specific values, and generated config are all expected under the repository root layout.
- Source evidence:
  `SE-023`, `SE-024`, `SE-025`, `SE-026`
- Impact:
  It is unclear which data belongs in the product repository, which belongs in a customer repository, and which should remain local runtime state only.
- Risk:
  Confidential or environment-specific content can drift into the wrong lifecycle boundary.
- Required TO-BE conditions:
  Explicit decision on product-source-only content versus external customer runtime content.

## 13. AS-IS Conclusion

Within the investigated repository scope, the current architecture is operationally capable but structurally mixed.

Confirmed facts from this investigation:

- Execution order already distinguishes Infra and Solution.
- Source layout does not enforce that distinction.
- One shared version catalogue drives both playbooks and acquisition scripts.
- Role logic owns chart-selection, values export, override rendering, and part of chart-contract validation.
- `install/` acts as both acquisition source area and materialized output area.
- Customer-editable configuration and generated configuration sit near product source.
- Scoped audit support exists for offline packages, but repository-standard rollback, resume, and state contracts were not found.

Those findings define the minimum problem set that the TO-BE design must address.
